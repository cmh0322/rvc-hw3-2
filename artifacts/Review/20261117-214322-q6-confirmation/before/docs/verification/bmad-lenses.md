# RVC BMAD 검토 관점

`bmad-review`가 선택한 관점만 읽고 적용한다. 공통 규약은 `docs/verification/review-contract.md`이다. 결과는 BMAD의 `location`, `trigger_condition`, `guard_snippet`, `potential_consequence` 필드를 유지하고 각 필드 안에 요구사항 근거와 구체적 위치를 포함한다. 최종 보고서에서 공통 규약의 분류·심각도·미검토 범위를 보충한다.

## adversarial

각 주장에 대해 “어떤 요구사항·상위 산출물이 이것을 정당화하는가?”, “이 주장이 틀리는 입력이나 경계 틱이 있는가?”를 묻는다. 원본 명세와 지적을 반증할 근거도 읽고 살아남은 지적만 보고한다. 최소 지적 개수를 요구하지 않는다. 결함이 확인되지 않으면 빈 결과와 검토 범위를 반환한다. 요구사항 밖 개선은 선택적 개선으로 구분한다.

## sasd

### 요구사항·이벤트·컨텍스트
- B1–B7 및 C1–C15의 동작·범위 제한을 구분하고 Q6를 가정으로 표시했는가?
- Front/Left/Right/Dust Sensor Input, Tick, Direction, Clean의 7개 외부 흐름이 이벤트 목록과 컨텍스트에서 방향·의미·외부 개체까지 대응하는가? 새 요구사항이 생겼다면 7이라는 숫자보다 원본을 우선한다.
- Tick 제어 흐름과 Direction/Clean 데이터 흐름의 분류가 일관적인가?

### DFD·사전·프로세스 명세
- Context↔Level 0↔1↔2↔3의 **각 부모 프로세스 경계**에서 입출력 집합·방향·의미가 보존되는가? 단순 전체 이름 비교로 부모별 balancing을 대신하지 않는다.
- 복합 데이터 분해·재결합은 사전 정의로 설명되는가? 내부 저장소/흐름과 외부 경계 흐름을 구분했는가?
- 프로세스 번호, 데이터/제어 구분, D1–D4의 내용과 reader/writer, 초기값과 갱신 순서가 대응하는가?
- 모든 Level 0–3 프로세스의 입력·출력·처리가 명세에 있는가? 입력만으로 출력을 결정할 수 있는가? Level 4에는 FSM을 사용했는가?
- Level 3에서 D4 advance → FSM 전이 → 출력/이동 상태 → D3 → 청소 결정 순서와 SD의 한 Tick 실행 순서가 의미적으로 일치하는가?

### FSM 및 구조적 설계
- Level 3 제어 인터페이스와 Level 4의 상태·전이·guard·action이 일치하는가? 모델 탐색 결과는 SPIN 단계에 맡기고, 문서 검토만으로 형식 검증 완료를 선언하지 않는다.
- Transform Analysis의 afferent/central/efferent 경계와 Structure Chart의 책임·호출 관계에 근거가 있는가?
- 매개변수·반환값과 데이터 사전이 일치하는가? DFD 화살표를 그대로 함수 호출로 옮기지 않았는가?
- 3.2.1의 값 전달, 3.2.3의 분리, 초기화/조정 모듈, 하드웨어 라이브러리, 숨긴 상태가 SA와 SD에 추적되는가?
- C9–C15 변경(첫 샘플·초기 출력·물걸레·미처리 먼지 포함)이 관련 문서에 전파됐는가? 승인 시점과 후속 결정 시점을 구분하는가?

### 구현·시스템 보고서가 범위에 포함될 때
- 설계와 코드 대조의 자세한 검사는 `rvc-c-compliance`, 수정 후 실행 검사는 `rvc-superpowers-verify`로 연결한다.
- 웹 시뮬레이터의 지도·센서 모델 가정과 사람의 PASS/FAIL 판정을 구분한다. 시나리오 수나 과거 로그만으로 이번 시스템 테스트 성공을 선언하지 않는다.
