## Subclaims and enforcement

1. **implemented — straight Forward command with cleaning during an eligible Tick.** `src/movement_controller.c:27-31,60` retains Forward if front is clear and ignores side classification in this branch. `src/assess_obstacle_situation.c:8-16` preserves the front bit independently of sides. `src/decide_actions.c:17-22` derives Forward status before choosing Clean; `src/derive_movement_status.c:8-12` maps only Forward to Forward status. `src/decide_cleaning.c:8-13` returns Start or Power Up for Forward, Stop for avoidance. `src/put_outputs.c:7-10` emits both outputs within the same cycle; `src/issue_movement_output.c:6-17` maps the Forward command to Direction Forward. Hardware straightness/trajectory is outside B6; the C-level obligation is the Direction command, not measured wheel motion.
2. **implemented — C16 side-only obstacles do not initiate avoidance in Forward.** All three possible side classifications reach the same `front_blocked == false` branch above. On blocked front the same FSM selects Stop and the cleaning mapping selects Stop. Turn completion returns Forward at `src/movement_controller.c:32-35`; subsequent Forward Ticks again use front. The side-only decision in Stopping/Backing at `:43-48` is a separate approved branch, not a C16 violation.
3. **contradicted — C13 prohibits startup Direction.** `src/initialize_rvc.c:10-13` obtains the reset command and calls `issue_movement_output`. `src/movement_controller.c:64-68` resets state and returns Forward; the output function invokes `drive_motor`. Main calls initialization before `wait_for_tick` (`src/main.c:12-16`). Thus Power On already sends Forward, with no matching Clean. No Clean during initialization is implemented, but the compound no-output obligation fails because Direction is emitted. Reinitialization repeats this behavior.
4. **contradicted — C12/approved SD initial acquisition boundary.** Initialization reads no sensor. The only production sensor acquisition is `controller → get_inputs → detect_obstacle/detect_dust`, after Main's `wait_for_tick` (`src/controller.c:10-13`, `src/get_inputs.c:11-14`, `src/detect_obstacle.c:10-12`, `src/detect_dust.c:8`). Reads precede decisions within that cycle, but do not satisfy the approved acquisition-before-first-Tick contract. There is no initial-validity/readiness gate or event acquisition path in the searched production interfaces. This is not a claim that the cycle uses uninitialized C local values: all four local values are read before decisions; the missing boundary and earlier motor output are the actual divergence.
