# RVC 검증 공통 규약

이 문서는 Codex 검증 도구의 프로젝트 적용 규칙이다. 요구사항이나 승인된 SA·SD를 대체하지 않는다. 경로는 프로젝트 루트 기준이다.

## 역할과 입력

| 진입 스킬 | 담당 | 입력 | 기본 결과 위치 |
|---|---|---|---|
| `rvc-bmad-review` | SA·SD의 내용·구조·설계 근거 검토 | 요구사항, SA, SD | `artifacts/Review/<run-id>/bmad/` |
| `rvc-speckit-review` | 문서 품질과 교차 추적성 | `.specify/rvc-review-map.toml`에 연결된 원본 | `artifacts/Review/<run-id>/traceability/` |
| `rvc-superpowers-verify` | 지적 타당성 확인, 승인된 수정, 재검증 | 리뷰 보고서, 변경 diff, 관련 테스트 | `artifacts/Review/<run-id>/verification/` |
| `rvc-c-compliance` | SA·SD → C 구현의 준수 여부 | 요구사항, SA·SD, `src/`, `include/`, `tests/` | `artifacts/Review/<run-id>/c-compliance/` |
| `rvc-fsm-verify` | FSM 모델과 속성 검증 | Level 3·4, 타이머 명세, 요구사항 | `artifacts/Review/<run-id>/fsm/` |

`run-id`는 실제 실행 시각과 구분 가능한 이름으로 정한다. 기존 보고서를 덮어쓰지 않는다. 설정 작성, 문서 검토, 코드 검사, 모델 검사, 시스템 테스트는 서로 다른 실행 상태로 기록한다.

## 근거의 우선순위

1. `AGENTS.md`: SASD 절차, 승인 경계, 생산 코드 C11/GCC, TDD·시스템 테스트 규칙.
2. `docs/preliminary_requirements.md`: 원문 7개 bullet을 기존 관례대로 B1–B7로 인용.
3. `docs/requirements_clarifications.md`: 확정 C1–C16을 사용하고 Q6는 C16으로 해결된 이력으로 구분. 충돌이 있으면 보고하고 임의로 해소하지 않는다.
4. `artifacts/SA/`, `artifacts/SD/`: 승인 기록과 이후 개정 범위를 확인한 뒤 해당 버전을 비교 기준으로 사용. 문서 안의 “Yes”, “approved”는 검토 이력의 주장이지 이번 실행의 검증 결과가 아니다.
5. `artifacts/Implementation/`, `artifacts/SystemTest/`: 기존 근거를 찾는 색인. 원본 코드·테스트·실행 로그를 다시 확인한다.

범위가 지정되지 않은 전반 리뷰는 SA → SD → 구현 → 시스템의 의존 순서를 따른다. 리뷰만 요청받았다면 원본 산출물·생산 코드·테스트를 바꾸지 않고 보고서와 검증용 파일만 작성한다. 수정 요청이 함께 있으면 그 범위 안에서 수정하되 SA→SD→TDD의 단계 진입 승인을 대신하지 않는다. 새 요구사항·가정 확정은 사람에게 맡긴다.

## RVC에서 혼동하면 안 되는 사항

- Q6는 2026-11-17 사용자 답변으로 C16에 확정되었다. Forward에서는 전방 장애물만 회피 시작 조건이며, 전방이 비어 있으면 좌우 장애물과 관계없이 전진·청소한다. 후진 종료 시 좌우로 판단하는 C9는 별개로 유지한다. 과거 보고서의 Q6 가정 표시는 당시의 이력이다.
- C4는 장애물이 물리적으로 사라지지 않는다는 조건이다. RVC가 이동·회전해도 센서값이 영원히 고정된다는 뜻이 아니다. 정지 중 전방 장애물이 유지된다는 현재 SA 해석은 출처를 별도로 기록한다.
- C9: 후진 종료 시 좌우로만 결정한다. C5의 후진 반복은 허용 동작이며 무조건 “언젠가 전진”한다는 요구사항은 없다.
- C3·C6·C7·C8의 5틱은 명령 발생 틱을 포함하는지 경계까지 확인한다. FSM의 예는 정지 t~t+4, 회전 t+5~t+9, 전진 t+10이다.
- C10은 진행 중 파워업을 먼지 재감지 시 재시작, C11은 회피 중 남은 파워업 틱을 보존한다. 청소 타이머 D3는 이동 FSM의 D4와 별개다. C15(2026-11-17)는 회피 중 감지를 기억하고 전진 복귀 시 5틱 재시작하도록 확정했다. 감지가 없으면 C11의 잔여 틱을 재개한다. C12는 첫 Tick 전 네 센서 읽기, C13은 초기화 시 출력 없음, C14는 흡입만 강화하고 물걸레는 정상 유지다. 현재 코드를 요구사항으로 역정의하지 않는다.
- B6에 따라 실제 하드웨어 구현은 범위 밖이다. `include/hw_interface.h` 선언, `tests/fake_hw.cpp`, `simulator/host/sim_host.c`를 구분한다.
- 생산 코드는 C11이고 GoogleTest 코드는 C++17이다. C++ 테스트가 있다는 이유로 C11 제약 위반이라고 지적하지 않는다.
- 파일 범위 `static` 상태는 정보 은닉 대상이다. 외부에서 접근 가능한 공유 상태와 구분한다. SD가 허용한 읽기 전용 상태 조회도 출처를 확인한다.
- DFD Level 0은 이 프로젝트에서 Process 0이다. 다른 교재의 번호 관례로 재번호화하지 않는다. Level 0–3의 모든 프로세스를 명세하되 Level 4 FSM에 별도 PSPEC을 만들지 않는다.
- 3.2.1의 매개변수 전달 구현, 3.2.3의 상태 도출/출력 분리는 SD의 설계 선택이다. 무조건 DFD 프로세스 1개=함수 1개를 강제하지 않는다.
- 배터리, 충전, SLAM, 앱 통신, 물리 충돌 방지 보장은 이 검토에서 새 기능으로 추가하지 않는다.

## 결과와 증거

보고서 머리말: 도구/스킬 및 버전, 범위, 읽은 파일과 절·줄, Git HEAD와 미커밋 변경 여부, 실행 시각, 실행/미실행 검사를 기록한다. 실제 입력 파일의 SHA-256을 남기면 미커밋 상태도 재현하기 쉽다.

각 지적: ID, 심각도, `확정 결함 / 요구사항 모호함 / 선택적 개선`, 근거 요구사항 ID, 양쪽 파일 위치, 반례·조건, 영향, 최소 수정안, 검증 상태. 도구 고유 판정과 심각도는 별도 열로 보존한다. 문서가 없다는 판정에는 검색 범위·표현·결과를 첨부한다.

지적 수의 최소 할당량은 없다. 근거 없는 항목은 제외한다. 반증된 지적도 사유를 남겨 반복 제안을 막는다. `해당 없음`은 근거를 요구하며 `미검토`와 구분한다.

테스트 성공, 문서 일관성, 모델 속성 성공, 실제 시스템 성공을 합쳐 하나의 PASS로 표시하지 않는다. 기존 README의 129개·100% 등의 수치를 이번 결과로 복사하지 않는다. 외부 스킬/Workflow 도구를 쓸 수 없으면 그 사실과 대체 방식, 미검증 범위를 명시한다.

## 원본 플러그인 찾기

BMAD와 Spec Kit은 `.agents/skills/`에 있다. Superpowers와 Trail of Bits는 현재 제공된 스킬 목록 또는 `codex plugin list`로 설치 상태를 찾고, 활성 플러그인의 실제 `SKILL.md`와 필요한 리소스를 읽는다. 개인 이름·버전별 캐시 경로를 팀 지침에 고정하지 않는다. 원본이 없어도 이름만으로 실행했다고 보고하지 않는다.
